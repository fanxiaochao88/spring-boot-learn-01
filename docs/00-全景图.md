# 第 00 章 全景图：从 CRUD 到微服务

> 预计用时：3 小时
> 本章不写代码，但可能是整套教程最重要的一章——它决定你后面是"背名词"还是"真理解"。

---

## 0.1 学习目标

读完本章，你应该能：

1. 用自己的话说清楚：为什么单体的 CRUD 项目会演变成微服务架构。
2. 画出公司系统的技术地图，并说出每个组件解决什么问题。
3. 理解"没有银弹"：每引入一个技术，都会带来新的复杂度。
4. 完成本地环境验证，为后面的动手实验做好准备。

---

## 0.2 先看看你现在的水平

你现在能写出来的系统，大概是这样的：

```text
浏览器 / 小程序
      │
      ▼
┌─────────────────────────────┐
│   Spring Boot 单体应用        │
│  Controller → Service → Mapper │
└─────────────────────────────┘
      │
      ▼
    MySQL
```

一个 `jar` 包，一台服务器，一个数据库。所有功能都在这一个进程里：

- 用户模块、商品模块、订单模块都是同一个项目里的不同包；
- 改一行代码，整个项目重新打包部署；
- 所有表都在同一个数据库里；
- 出了问题，查一个日志文件；
- 流量大了，就加一台机器、再复制一份应用（但数据库还是那一个）。

**这个架构不丢人。** 事实上，大多数公司的早期系统、内部管理系统、中小型项目，到今天仍然这么跑。它简单、开发快、排查容易。

问题出现在业务增长之后。

---

## 0.3 单体架构会遇到的六个问题

我们不用抽象地说"业务变大"，而是具体看六个场景。**请记住这六个场景，后面每个技术都对应其中至少一个。**

### 问题 1：代码越来越难改

项目从 5 个接口变成 500 个接口，从 3 个人变成 30 个人。所有人都在同一个仓库里改代码：

- 你改用户模块，导致商品模块编译不过；
- 两个人在同一个 `Service` 文件里解决冲突；
- 想复用一小段代码，结果引入了一堆无关依赖；
- 新人入职，看 20 万行代码不知道从哪下手。

→ 对应技术：**服务拆分、微服务**（第 04 章）

### 问题 2：一处故障，全站挂掉

所有功能在同一个进程里。商品模块的一个死循环、一次内存泄漏，会把整个应用拖垮——用户登录、下单、支付全部不可用。

→ 对应技术：**服务隔离、熔断降级**（第 05 章 Sentinel）

### 问题 3：无法按需扩容

双十一流量是平时的 20 倍，但主要是订单和商品查询压力大，用户登录模块并不需要扩容。单体应用只能整个复制，浪费机器。

→ 对应技术：**微服务 + 独立扩容 + 网关限流**（第 04、05 章）

### 问题 4：数据库成为瓶颈

所有读写打在一个 MySQL 上。商品详情页每秒几万次查询，把数据库连接池打满，导致下单写库也变慢。

→ 对应技术：**Redis 缓存**（第 03 章）、**读写分离/分库分表**（第 02 章概念）

### 问题 5：耗时操作拖慢主流程

下单接口需要：校验库存 → 创建订单 → 扣库存 → 加积分 → 发短信 → 写日志。前四步必须同步完成，后面的加积分、发短信、写日志其实可以慢慢做。但同步执行让接口响应从 200ms 变成 2 秒。

→ 对应技术：**消息队列 Kafka**（第 06 章）

### 问题 6：配置和部署混乱

10 个服务，每个服务都有数据库地址、Redis 地址、开关配置。改一个配置要登录 10 台服务器；某个服务重启后，调用方不知道新实例的 IP 是多少。

→ 对应技术：**Nacos 配置中心 + 注册中心**（第 04 章）、**Docker 部署**（第 08 章）

## 0.4 架构演进：不是一步到位的

很多新人以为"公司都用微服务，所以单体是错的"。真实情况是：**架构是随着问题一步步演进的，而且常常是混合的。**

```text
第 1 阶段：单体
  一个应用 + 一个数据库
        │
        │ 问题：代码耦合、无法独立扩容
        ▼
第 2 阶段：垂直拆分
  用户应用 / 商品应用 / 订单应用（各自独立部署，可能共用数据库）
        │
        │ 问题：服务之间怎么调用？地址怎么管理？
        ▼
第 3 阶段：服务化（SOA / 微服务）
  服务注册发现（Nacos）+ 远程调用（Feign）+ 网关（Gateway）
        │
        │ 问题：流量、故障、数据一致性、可观测性
        ▼
第 4 阶段：云原生
  容器化（Docker/K8s）+ 消息队列 + 缓存 + 监控告警 + 服务网格
```

关键认知：

1. **微服务不是目的，是手段。** 目的是让团队能独立开发、独立部署、独立扩容、故障隔离。
2. **拆得越细，运维成本越高。** 一个 3 人团队维护 20 个微服务，是灾难。
3. **公司里往往既有微服务，也有单体。** 后台管理系统、定时任务、内部工具，单体反而更合适。

## 0.5 技术地图：每个组件到底是干什么的

把公司架构想象成一栋大楼：

```text
                       用户 / 小程序 / App
                              │
                              ▼
                    ┌──────────────────┐
                    │  Nginx / 负载均衡  │   ← 接入层：分发流量、HTTPS
                    └──────────────────┘
                              │
                              ▼
                    ┌──────────────────┐
                    │  API 网关 Gateway  │   ← 统一入口：路由、鉴权、限流
                    └──────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
 ┌─────────────┐       ┌─────────────┐       ┌─────────────┐
 │ 用户服务     │       │ 商品服务     │       │ 订单服务     │   ← 业务层
 │ Spring Boot │◄─────►│ Spring Boot │◄─────►│ Spring Boot │
 └─────────────┘ Feign └─────────────┘ Feign └─────────────┘
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   ┌─────────┐          ┌─────────┐          ┌─────────┐
   │  MySQL  │          │  Redis  │          │  Kafka  │   ← 支撑层
   │ 持久化   │          │ 缓存/锁  │          │ 异步消息 │
   └─────────┘          └─────────┘          └─────────┘

   Nacos：服务注册与配置中心（横跨所有服务）
   Sentinel：限流熔断（横跨所有服务）
   Seata：分布式事务（跨服务数据一致性）
   Prometheus + Grafana + 链路追踪：监控与排错
   Docker / K8s：部署与运维
```

### 逐组件速查表

| 组件 | 一句话职责 | 解决 0.3 节的哪个问题 | 本教程章节 |
|---|---|---|---|
| **Nacos** | 服务注册中心 + 配置中心：服务能互相找到，配置能集中管理并热更新 | 问题 6 | 04 |
| **OpenFeign** | 声明式 HTTP 调用：像调本地方法一样调远程服务 | 问题 1、6 | 04 |
| **Spring Cloud Gateway** | API 网关：所有请求的统一入口，做路由、鉴权、限流 | 问题 2、3 | 05 |
| **Sentinel** | 流量防卫兵：限流、熔断、降级、热点保护 | 问题 2、3 | 05 |
| **Redis** | 内存缓存 + 分布式锁 + 计数器 | 问题 4 | 03 |
| **Kafka** | 消息队列：异步、解耦、削峰 | 问题 5 | 06 |
| **Seata** | 分布式事务框架：跨服务操作要么全成功要么全失败 | 问题 5 的进阶 | 07 |
| **Docker** | 容器化：把应用和依赖打包，一键运行 | 问题 6 | 08 |
| **Prometheus / Grafana** | 指标采集与可视化监控 | 问题 2 | 09 |
| **链路追踪（SkyWalking 等）** | 把一次请求经过的所有服务串起来 | 问题 2 | 09 |
| **Elasticsearch** | 全文搜索、日志检索 | 问题 4 的搜索场景 | 11 章提及 |

### 一个重要区分：Nacos 的两个功能

新手最容易混淆：Nacos 同时是**注册中心**和**配置中心**，这是两个独立功能。

- **注册中心**：商品服务启动后告诉 Nacos"我在 192.168.1.10:8081"，订单服务要调商品服务时问 Nacos"商品服务在哪"。解决**服务地址动态变化**的问题。
- **配置中心**：把 `application.yml` 里的配置放到 Nacos 上，改完不用重启服务。解决**配置分散、修改麻烦**的问题。

第 04 章会把两者分开讲清楚。

## 0.6 微服务带来的新问题（必须提前知道）

只讲好处是不负责任的。拆成微服务后，你会立刻遇到：

| 新问题 | 具体表现 | 解决方向 |
|---|---|---|
| **调用失败** | 网络抖动、对方服务挂了，Feign 调用超时 | 超时、重试、熔断降级（05 章） |
| **数据一致性** | 订单创建成功，但扣库存失败，数据不一致 | 分布式事务、本地消息表（07 章） |
| **排查困难** | 一次请求经过 5 个服务，报错日志散落在 5 台机器 | 链路追踪、统一 traceId（09 章） |
| **重复消费** | Kafka 消息重复投递，积分加了两次 | 幂等设计（06、07 章） |
| **分布式锁** | 两个实例同时扣同一件库存 | Redis / Redisson 分布式锁（03、07 章） |
| **部署复杂** | 10 个服务、5 个中间件，手工安装要一天 | Docker Compose（08 章） |
| **版本管理** | 服务 A 升级接口，服务 B 不兼容 | 接口版本化、契约测试 |

**这就是为什么第 07 章要专门讲"分布式难题"**。微服务不是免费的午餐，它是用"分布式复杂度"换"组织和扩展能力"。

### CAP 与 BASE：面试常问，但先理解直觉

- **CAP**：一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可同时满足。分布式系统必然有网络分区，所以实际上是在 **CP** 和 **AP** 之间取舍。
  - 银行转账：更偏 CP，宁可暂时不可用，也不能算错账。
  - 商品详情页：更偏 AP，短暂看到旧价格可以接受，但不能打不开。
- **BASE**：Basically Available（基本可用）、Soft state（软状态）、Eventually consistent（最终一致性）。很多互联网系统选择"先响应，最终一致"。
  - 下单后积分晚 2 秒到账，用户能接受；但下单接口等 2 秒，用户就跑了。

第 07 章会把这些概念落到具体方案上。

## 0.7 怎么读公司代码：一张"入口地图"

等你进公司或参与项目，不要从第一行代码开始读。按这个顺序：

1. **先看 `pom.xml` / 依赖**：用了哪些技术，版本是什么。这决定了系统的"技术骨架"。
2. **看启动类和配置文件**：`application.yml`、`bootstrap.yml`，有没有 Nacos 地址、数据库、Redis、Kafka 配置。
3. **看 Controller**：系统对外提供哪些接口，这是业务入口。
4. **挑一个核心接口，跟一条完整链路**：Controller → Service → Mapper → 数据库，中间有没有 Feign、Redis、MQ。
5. **看异常处理和日志**：出问题时从哪里查。
6. **最后看基础设施代码**：网关配置、公共模块、工具类。

本章练习会让你用这套方法分析一个真实项目（可以是公司的，也可以是第 10 章的示例项目）。

## 0.8 动手实验：搭建本地环境

后面的章节需要一个能跑的本地环境。请现在完成。

### 实验 1：验证基础工具

```bash
java -version
mvn -v
docker --version
docker compose version
```

如果 `java -version` 不是 17，请先安装 JDK 17 并配置 `JAVA_HOME`。

### 实验 2：拉取镜像

```bash
docker pull mysql:8.0
docker pull redis:7.2
docker pull nacos/nacos-server:v2.3.2
docker pull bitnami/kafka:3.7
```

> 国内网络慢是正常的，可以边拉边读后面的章节。实在拉不下来，先完成概念部分，第 08 章会讲镜像加速。

### 实验 3：启动最小环境（MySQL + Redis）

进入教程的 `docker` 目录（第 08 章会给出完整的 compose 文件，这里先验证 Docker 能用）：

```bash
cd docker
docker compose up -d mysql redis
docker compose ps
```

看到两个容器状态为 `running` 即成功。然后验证：

```bash
docker exec -it roadmap-mysql mysql -uroot -p123456 -e "select version();"
docker exec -it roadmap-redis redis-cli ping
```

预期输出：MySQL 版本号；Redis 返回 `PONG`。

> 如果你还没有 `docker/docker-compose.yml`，可以跳到第 08 章先把文件复制过来，或者等学完第 08 章再回来做这个实验。**环境不是当前必须的，但越早跑通越好。**

### 实验 4：记录你的环境

新建一个 `env.md`，写下：

```markdown
- JDK: 
- Maven: 
- Docker: 
- 操作系统: 
- 遇到的问题及解决:
```

## 0.9 常见误区

| 误区 | 正确认知 |
|---|---|
| "公司用微服务，所以单体过时了" | 微服务是组织和技术规模到了才划算的选择；大多数项目单体足够 |
| "技术越多越厉害" | 每多一个组件，就多一个故障点、一套运维成本。能不用就不用 |
| "先学完所有技术再做项目" | 应该在项目里按需学，学完立刻用 |
| "Nacos 就是注册中心" | 它还是配置中心，两者解决不同问题 |
| "用了 MQ 就解耦了" | 用不好会引入消息丢失、重复消费、顺序错乱等新问题 |
| "分布式事务必须强一致" | 大多数业务能接受最终一致，强一致代价极高 |

## 0.10 练习题

1. **画地图**：找一张纸，画出你公司系统（或你知道的某个系统）的架构草图。至少标出：入口、服务、数据库、缓存、消息队列、注册中心。标不出来的就写问号，后面学到时回来补。
2. **对号入座**：把 0.3 节的六个问题，分别对应到你自己的 CRUD 项目。如果项目数据量很小，试着想象"如果用户量涨 1000 倍"会先出什么问题。
3. **术语解释**：不看本章，用自己的话解释：注册中心、网关、消息队列、缓存、分布式事务。每个不超过两句话。
4. **思考题**：一个只有 3 个开发、日活 5000 的内部管理系统，需要上微服务吗？为什么？
5. **环境**：完成 0.8 节的实验，记录结果。

## 0.11 本章小结

三句话：

1. **微服务不是新技术堆砌，而是单体遇到"代码、故障、扩容、数据库、耗时、配置"六类问题后的演进结果。**
2. **每个中间件都对应解决一个具体问题，同时引入新的复杂度；理解 trade-off 比记住名词重要。**
3. **接下来先补工程化和数据库、缓存，再拆服务、加网关和消息队列，最后用 Docker 串起来。**
