一、自定义校验注解（Bean Validation）
1. 自定义校验注解的结构
   自定义校验注解 = 注解声明（@Constraint）+ 校验器实现（ConstraintValidator） 两个文件。

注解里 message() / groups() / payload() 是规范强制要求，groups/payload 几乎不用但必须写，否则报错。

校验器只实现一个 boolean isValid(T value, Context ctx) 方法。

null 返回 true 是行业惯例：格式校验与必填校验分离，必填交给 @NotNull/@NotBlank。

2. 编译错误排查
   Incompatible types: Class<PhoneValidator>, required Class<? extends ConstraintValidator<?,?>>[]

根因：PhoneValidator 没实现 jakarta.validation.ConstraintValidator，最常见是项目里 javax.validation 和 jakarta.validation 混用。排查导入包 + mvn dependency:tree 排依赖。

3. 为什么校验注解"看起来复杂"，AOP 标记注解"很简单"
   注解本身只是元数据，复杂度取决于"谁来解释它"。

AOP 标记注解：解释权在你（切面），注解可以极简。

校验注解：解释权在 Bean Validation 框架，必须按框架协议填属性 + 提供校验器。

记忆模板：注解骨架照抄 + 校验器只写 isValid 布尔逻辑。

二、Java 正则
1. 为什么要 Pattern.compile()
   不是 Java 强制编译，而是 Java 把编译显式化。JS 的 /.../ 字面量也在编译，只是语法糖隐藏了。

Java 无正则字面量语法，正则只是 java.util.regex 库；Pattern = 编译结果（线程安全、可复用），Matcher = 一次匹配（有状态、不共享）。

性能规范：正则用 static final Pattern 预编译，别在循环/高频路径用 String.matches()（内部每次 compile）。

Java 字符串里正则要写 \\d（字符串转义），JS 字面量 /\d/ 免转义。

2. .matcher(value).matches() 拆解
   两步：matcher(value) 创建匹配器（绑定规则+文本，不执行）→ matches() 执行整串匹配。

matches() = 隐式 ^...$，要求整个字符串完全匹配；find() 找子串；lookingAt() 只要求前缀。

Pattern 编译一次全局复用；Matcher 每次新建（线程不安全，别跨线程/跨输入复用）。

类比：Pattern = 标准答案，matcher = 批改器，matches() = 整卷是否全对。

三、MyBatis 注解
@Mapper vs @MapperScan
@Mapper（MyBatis 原生）：加在单个接口上，手动逐个标记。

@MapperScan（mybatis-spring）：加在启动类，指定包路径批量扫描该包下所有接口。

推荐用 @MapperScan，一次搞定；用了它之后 @Mapper 就不是必须的。二者通常二选一。

四、Controller 参数校验
1. 技术栈与用法
   技术：Jakarta Bean Validation（Hibernate Validator 实现），依赖 spring-boot-starter-validation（spring-boot-starter-web 不含它，必须显式加）。

链路：依赖引入 → DTO 加约束注解 → Controller 加 @Valid/@Validated → 全局异常处理器统一返回错误。

@RequestBody 对象：参数前加 @Valid，失败抛 MethodArgumentNotValidException。

嵌套对象必须在字段上加 @Valid，否则内部约束静默跳过。

2. @Validated 干什么
   @Valid 的 Spring 增强版，两大作用：

让非对象参数（@PathVariable/@RequestParam）的校验生效：必须在 Controller 类上加 @Validated，Spring 才创建 AOP 代理执行校验。
分组校验：@Validated(Create.class) 指定分组，解决"新增/修改不同规则"。
坑点：指定了分组后，没标 groups 的注解默认属于 Default 组，不会执行，需显式声明 groups = {Create.class, Update.class}。

Spring Boot 3.2+ 内置方法级校验，可不再依赖类级 @Validated（新旧机制别混用）。

五、Integer 比较与 NPE
1. status == 1 的风险
   status 为 null 时，== 1 触发自动拆箱 → NPE。

两个 Integer 用 == 比的是引用：-128~127 有缓存返回 true，超出范围返回 false（诡异行为）。

两个 Integer 比值永远用 equals，永不 ==。

2. 正确写法
   java
   Integer.valueOf(1).equals(status)      // 最安全，null 也安全
   status != null && status == 1          // 判空后拆箱，注意 && 短路顺序
   Objects.equals(status, 1)              // 两边都可能 null
   常量在左（Yoda 条件）：常量.equals(变量)，调用者永不 null。

status.equals(1) 调用者是 status，为 null 照样 NPE。

3. 代码赏析
   java
   vo.setStatusText(Integer.valueOf(1).equals(product.getStatus()) ? "上架" : "下架");
   好在三点：equals 比值不踩引用坑 + 常量在左不怕 null + 三元表达式无副作用完成映射。可优化：魔法数字 1 提成常量或枚举。

六、equals 的本质
equals 比的是"类作者定义的逻辑相等"，不是天然"比值"。

Object.equals 默认实现是 this == obj（比引用）。

Integer/String/BigDecimal 等重写了 equals，才比值（Integer.equals 源码比 intValue()，且先 instanceof 判断类型）。

没重写 equals 的类（如自己写的 POJO 不重写），equals 和 == 一样比引用。

BigDecimal 坑：1.0 和 1.00 equals 为 false（比数值+精度），比值用 compareTo。

重写 equals 必须同时重写 hashCode（Java 硬性契约，否则 HashMap/HashSet 出 bug）。

七、贯穿性设计思想（最值得记的"元知识"）
注解只是元数据，复杂度在"解释器"：AOP 注解、校验注解、@Transactional、@Cacheable 背后都有拦截器/代理/处理器，注解只是给它们看的"配置单"。

显式优于隐式：Java 把 Pattern.compile、equals 重写、Matcher 状态都摆到台面，让你可控可复用；JS 用语法糖隐藏。

防御式编程三件套：常量在左防 NPE、equals 比值防引用坑、三元表达式/短路求值减少分支副作用。

规范强制 vs 业务自定义：groups/payload 是规范强制（照抄），message/校验逻辑才是你写的——别被模板吓到。
