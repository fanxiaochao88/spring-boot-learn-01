# 第 09 章 可观测性

> 预计用时：6 小时
> 微服务出问题时，日志散落在 5 台机器、一次请求经过 6 个服务。没有可观测性，排查基本靠猜。

---

## 9.1 学习目标

读完并动手后，你能：

1. 说清楚可观测性的三大支柱：日志、指标、链路追踪。
2. 给所有服务加统一 traceId，把一次请求串起来。
3. 用 Actuator + Micrometer + Prometheus + Grafana 做指标监控。
4. 用 Micrometer Tracing + Zipkin 看调用链。
5. 设计日志规范、告警规则和排错流程。
6. 知道什么时候该上 SkyWalking 这类 APM。

---

## 9.2 什么是可观测性

传统监控只回答"系统挂没挂"。可观测性要回答：

- **发生了什么？**（日志）
- **系统现在什么状态？**（指标）
- **这次请求经过了哪些服务，慢在哪？**（链路追踪）

### 9.2.1 三大支柱

| 支柱 | 数据形态 | 回答的问题 | 工具 |
|---|---|---|---|
| **Logs 日志** | 文本/JSON 事件 | 具体发生了什么错误 | ELK、Loki、SLF4J |
| **Metrics 指标** | 数值时间序列 | QPS、延迟、错误率、CPU | Micrometer、Prometheus、Grafana |
| **Traces 链路** | 调用树 + span | 一次请求经过哪些服务、各段耗时 | Zipkin、SkyWalking、Jaeger |

### 9.2.2 排错时的使用顺序

```text
1. 告警：错误率上升 / P99 延迟升高（Metrics）
2. 定位服务：看哪个服务的指标异常（Metrics + 链路）
3. 定位请求：找一条慢请求，看调用链哪一段慢（Traces）
4. 定位原因：看该服务的日志和异常堆栈（Logs）
5. 修复并验证
```

## 9.3 日志规范与 traceId

### 9.3.1 日志要包含什么

一条好的业务日志至少包含：

- **时间**（精确到毫秒）
- **级别**
- **traceId**（串联一次请求）
- **线程**
- **类名**
- **业务标识**（订单号、用户 ID）
- **关键参数**（脱敏后）
- **结果/耗时**

示例：

```text
2026-11-09 10:30:01.123 [http-nio-8082-exec-1] INFO  [a1b2c3d4e5f6] c.e.m.order.OrderService - 创建订单开始 userId=1 productId=1001 quantity=2
2026-11-09 10:30:01.456 [http-nio-8082-exec-1] INFO  [a1b2c3d4e5f6] c.e.m.order.OrderService - 创建订单成功 orderId=9001 cost=333ms
```

### 9.3.2 实现 traceId 过滤器

```java
package com.example.mall.common.web;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.UUID;

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    public static final String TRACE_ID = "traceId";
    public static final String TRACE_HEADER = "X-Trace-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        // 上游已传递则复用，否则生成
        String traceId = request.getHeader(TRACE_HEADER);
        if (!StringUtils.hasText(traceId)) {
            traceId = UUID.randomUUID().toString().replace("-", "").substring(0, 16);
        }

        MDC.put(TRACE_ID, traceId);
        response.setHeader(TRACE_HEADER, traceId);

        try {
            filterChain.doFilter(request, response);
        } finally {
            MDC.remove(TRACE_ID);
        }
    }
}
```

### 9.3.3 跨服务传递

Feign 拦截器（第 04 章已经写过）：

```java
@Bean
public RequestInterceptor traceInterceptor() {
    return template -> {
        String traceId = MDC.get(TraceIdFilter.TRACE_ID);
        if (traceId != null) {
            template.header(TraceIdFilter.TRACE_HEADER, traceId);
        }
    };
}
```

Kafka 消息也要传：

```java
// 生产
ProducerRecord<String, Object> record = new ProducerRecord<>(topic, key, event);
record.headers().add("X-Trace-Id", MDC.get("traceId").getBytes(StandardCharsets.UTF_8));
kafkaTemplate.send(record);

// 消费
@KafkaListener(...)
public void onMessage(ConsumerRecord<String, OrderCreatedEvent> record, Acknowledgment ack) {
    Header header = record.headers().lastHeader("X-Trace-Id");
    if (header != null) {
        MDC.put("traceId", new String(header.value(), StandardCharsets.UTF_8));
    }
    try {
        // 处理
        ack.acknowledge();
    } finally {
        MDC.clear();
    }
}
```

> 异步线程池也要传递 MDC，否则子线程日志没有 traceId。用 `TaskDecorator`：

```java
@Bean
public TaskDecorator mdcTaskDecorator() {
    return runnable -> {
        Map<String, String> context = MDC.getCopyOfContextMap();
        return () -> {
            if (context != null) {
                MDC.setContextMap(context);
            }
            try {
                runnable.run();
            } finally {
                MDC.clear();
            }
        };
    };
}
```

### 9.3.4 日志输出格式

第 01 章的 `logback-spring.xml` 已经包含 `%X{traceId}`：

```xml
<pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [%X{traceId}] %logger{36} - %msg%n</pattern>
```

如果要接入 ELK/Loki，建议输出 **JSON 格式**，便于检索：

```xml
<encoder class="net.logstash.logback.encoder.LogstashEncoder">
    <customFields>{"app":"mall-product"}</customFields>
</encoder>
```

需要依赖 `net.logstash.logback:logstash-logback-encoder`。

### 9.3.5 日志级别与规范

- **ERROR**：需要人处理。每条 ERROR 都应该有告警或工单。
- **WARN**：业务异常、可恢复问题。不要滥用。
- **INFO**：关键业务节点。每个请求 1-3 条，不要每行都打。
- **DEBUG**：开发排查用，生产默认关闭，可按包临时打开。

**禁止：**

- 在循环里逐条打 INFO；
- 打印完整大对象；
- 打印密码、token、身份证、银行卡；
- 用 `System.out.println`；
- 日志里拼接字符串（用占位符）。

## 9.4 指标监控：Actuator + Micrometer + Prometheus

### 9.4.1 依赖

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

### 9.4.2 配置

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      show-details: always
  metrics:
    tags:
      application: ${spring.application.name}
  prometheus:
    metrics:
      export:
        enabled: true
```

验证：

```bash
curl http://localhost:8081/actuator/prometheus
```

会输出大量指标：

```text
# HELP http_server_requests_seconds
# TYPE http_server_requests_seconds summary
http_server_requests_seconds_count{application="product-service",method="GET",status="200",uri="/api/products/{id}",} 1523.0
http_server_requests_seconds_sum{...} 45.2
jvm_memory_used_bytes{application="product-service",area="heap",} 1.23E8
hikaricp_connections_active{application="product-service",pool="HikariPool-1",} 3.0
```

### 9.4.3 关键指标

| 指标 | 含义 | 关注点 |
|---|---|---|
| `http_server_requests_seconds` | 接口耗时分布 | P95/P99 延迟、错误率 |
| `http_server_requests_seconds_count` | 请求数 | QPS |
| `jvm_memory_used_bytes` | JVM 内存 | 是否持续增长（泄漏） |
| `jvm_gc_pause_seconds` | GC 停顿 | 长停顿、频繁 Full GC |
| `hikaricp_connections_active` | 数据库连接数 | 是否接近上限 |
| `system_cpu_usage` | CPU | 是否打满 |
| `lettuce_command_completion` | Redis 命令 | 慢命令 |
| `kafka_consumer_fetch_manager_records_lag` | Kafka 积压 | 消费是否跟不上 |

### 9.4.4 自定义业务指标

```java
@Service
@RequiredArgsConstructor
public class OrderMetrics {

    private final MeterRegistry meterRegistry;

    @PostConstruct
    public void init() {
        // 计数器：订单创建成功/失败
        Counter.builder("mall.order.created")
                .description("订单创建数量")
                .tag("result", "success")
                .register(meterRegistry);

        // Gauge：当前库存（示例，实际应从业务读取）
        Gauge.builder("mall.product.stock", this, OrderMetrics::getStock)
                .tag("productId", "1001")
                .register(meterRegistry);
    }

    public void recordCreated(boolean success) {
        meterRegistry.counter("mall.order.created", "result", success ? "success" : "fail").increment();
    }

    public void recordCost(long millis) {
        meterRegistry.timer("mall.order.cost").record(Duration.ofMillis(millis));
    }

    private double getStock() {
        return 100;
    }
}
```

### 9.4.5 启动 Prometheus + Grafana

```bash
cd docker
docker compose -f observability-compose.yml up -d
```

- Prometheus：`http://localhost:9090`
- Grafana：`http://localhost:3000`（admin/admin）
- Zipkin：`http://localhost:9411`

Prometheus 配置见 `docker/prometheus/prometheus.yml`。

Grafana 接入：

1. Configuration → Data Sources → Add Prometheus；
2. URL 填 `http://prometheus:9090`（同在 compose 网络）；
3. 导入 Spring Boot 看板：Dashboard → Import → 输入 ID `4701` 或 `19004`；
4. 观察 QPS、P95、JVM、连接池曲线。

### 9.4.6 告警规则（概念）

Prometheus 告警示例：

```yaml
groups:
  - name: mall-alerts
    rules:
      - alert: HighErrorRate
        expr: |
          sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
          /
          sum(rate(http_server_requests_seconds_count[5m])) > 0.05
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "5xx 错误率超过 5%"

      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            sum(rate(http_server_requests_seconds_bucket[5m])) by (le, uri)
          ) > 2
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "P99 延迟超过 2 秒"
```

> 告警要少而准。每个告警都要有明确的处理动作，否则会变成"告警疲劳"。

## 9.5 链路追踪：Micrometer Tracing + Zipkin

### 9.5.1 依赖

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-tracing-bridge-brave</artifactId>
</dependency>
<dependency>
    <groupId>io.zipkin.reporter2</groupId>
    <artifactId>zipkin-reporter-brave</artifactId>
</dependency>
```

### 9.5.2 配置

```yaml
management:
  tracing:
    sampling:
      probability: 1.0       # 本地全采样；生产建议 0.1 或按需
  zipkin:
    tracing:
      endpoint: http://localhost:9411/api/v2/spans
```

### 9.5.3 自动埋点范围

Spring Boot 3 + Micrometer Tracing 自动为以下组件生成 span：

- HTTP 入口（Spring MVC / WebFlux）；
- RestTemplate / WebClient；
- OpenFeign；
- Kafka 生产/消费；
- 数据库调用（部分）；
- Redis（部分）。

**你几乎不用改代码。** 启动 Zipkin，访问一次订单接口，打开 `http://localhost:9411`，就能看到调用树：

```text
order-service  POST /api/orders            320ms
├── product-service  GET /api/products/1001  45ms
├── product-service  POST /api/products/1001/decrease  60ms
└── mysql  INSERT orders                    12ms
```

### 9.5.4 与自建 traceId 的关系

- Micrometer Tracing 会自动生成 `traceId` 和 `spanId`，并写入 MDC；
- 如果你已经有 `TraceIdFilter`，两者可能冲突或重复。**二选一**：
  - 学习/轻量：用自建 traceId，简单可控；
  - 生产/完整：用 Micrometer Tracing + Zipkin/SkyWalking。

> 如果同时使用，建议以 Micrometer Tracing 为准，删掉自建过滤器，并在日志 pattern 里用 `%X{traceId}`（Micrometer 会自动填充）。

### 9.5.5 SkyWalking（了解）

| 维度 | Zipkin + Micrometer | SkyWalking |
|---|---|---|
| 侵入性 | 低（自动配置） | 无（Java Agent） |
| 功能 | 链路追踪 | 链路 + 指标 + 拓扑 + 告警 |
| 部署 | 简单 | 需要 OAP + UI + ES |
| 国内使用 | 较多 | 很多 |

SkyWalking 通过 `-javaagent:skywalking-agent.jar` 挂载，不改代码。公司里如果已有 SkyWalking，优先用它。

## 9.6 健康检查与就绪探针

```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true
      show-details: always
```

端点：

- `/actuator/health/liveness`：进程活着吗？失败时重启容器。
- `/actuator/health/readiness`：能接收流量吗？失败时从负载均衡摘除。
- `/actuator/health`：综合状态（数据库、Redis、磁盘等）。

K8s 配置示例：

```yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8081
  initialDelaySeconds: 30
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8081
  initialDelaySeconds: 20
  periodSeconds: 5
```

> 数据库连接失败时，`readiness` 应该失败（不接流量），但 `liveness` 不应失败（否则容器被反复重启，问题更糟）。

## 9.7 一次完整的排错演练

**现象**：用户反馈"下单很慢，有时失败"。

**步骤：**

1. **看监控**：Grafana 里 `POST /api/orders` 的 P99 从 300ms 涨到 3s，5xx 错误率 8%。
2. **看链路**：Zipkin 找一条慢请求，发现 `product-service` 的 `POST /decrease` 耗时 2.5s。
3. **看商品服务指标**：数据库连接池 `hikaricp_connections_active` 接近上限，`http_server_requests` 中该接口 P99 很高。
4. **看商品服务日志**：大量 `Deadlock found when trying to get lock` 和慢 SQL。
5. **定位 SQL**：`UPDATE product SET stock = stock - ? WHERE id = ?` 没加索引？实际有主键，但事务里还调了远程接口，导致锁持有时间长。
6. **修复**：把远程调用移出事务；库存扣减改为条件更新；加 Redis 分布式锁限流。
7. **验证**：压测 P99 回到 200ms，死锁消失。
8. **加告警**：连接池使用率 > 80%、死锁次数 > 0、P99 > 1s。

> 这个流程的核心是：**指标定位服务 → 链路定位环节 → 日志定位原因**。

## 9.8 常见坑

1. **只有日志，没有指标和链路**：出问题只能 grep，效率极低。
2. **traceId 没跨服务传递**：每个服务都生成新的，链路断开。
3. **异步线程丢 MDC**：线程池里的日志没有 traceId。
4. **Kafka 消费丢 traceId**：消息头没传，消费端日志孤立。
5. **采样率 100% 打到生产**：链路数据量爆炸，存储扛不住。生产 1%-10% 起步。
6. **指标标签基数爆炸**：把 `userId`、`orderId` 作为 tag，导致时间序列无限增长。**标签只能是有限的枚举值**。
7. **日志级别全开 DEBUG**：磁盘写满、性能下降。
8. **告警阈值拍脑袋**：要么天天误报，要么真出事不报。基于历史 P99 和业务目标设定。
9. **健康检查把数据库当 liveness**：数据库抖动导致容器被反复重启。
10. **敏感信息进日志**：合规事故。

## 9.9 动手实验

### 实验 1：traceId 串联

1. 给订单服务和商品服务加 `TraceIdFilter`；
2. 给 Feign 加传递拦截器；
3. 调用下单接口；
4. 在两个服务的日志里搜索同一个 traceId，确认能串起来。

### 实验 2：Prometheus + Grafana

1. 启动 `observability-compose.yml`；
2. 访问 `http://localhost:9090/targets`，确认服务是 UP；
3. Grafana 导入 Spring Boot 看板（ID 19004）；
4. 压测下单接口，观察 QPS、P99、JVM 内存曲线。

### 实验 3：Zipkin 链路

1. 加 Micrometer Tracing + Zipkin 依赖；
2. 配置 endpoint；
3. 调用下单接口；
4. 在 Zipkin 里按服务名搜索，查看调用树和各 span 耗时。

### 实验 4：制造慢调用

在商品服务里随机 `sleep(2000)`，观察：
- Grafana P99 上升；
- Zipkin 中商品服务 span 变长；
- 日志里 traceId 对应的请求耗时。

### 实验 5：Kafka 链路

发送订单消息，在 Zipkin 中观察生产者和消费者的 span 是否关联（配置正确时，Kafka 头会传递 trace 上下文）。

## 9.10 练习题

1. 实现 traceId 的全链路传递：HTTP → Feign → Kafka → 消费者。
2. 自定义一个业务指标"订单创建成功率"，并在 Grafana 中展示。
3. 配置一条告警：5 分钟内 5xx 错误率超过 5% 时触发。
4. 用 Zipkin 找出一次调用中耗时最长的 span，并解释原因。
5. **思考题**：为什么不能把 `userId` 作为 Prometheus 指标的 tag？
6. **思考题**：liveness 和 readiness 的区别是什么？数据库挂了应该让哪个失败？
7. **思考题**：日志、指标、链路三者能否互相替代？为什么？

## 9.11 本章小结

1. **可观测性 = 日志 + 指标 + 链路**，三者互补，缺一不可。
2. **traceId 是串联微服务日志的关键**，要跨 HTTP、Feign、Kafka、线程池传递。
3. **Actuator + Micrometer + Prometheus + Grafana** 是 Spring Boot 指标监控的标准组合。
4. **Micrometer Tracing + Zipkin/SkyWalking** 自动生成调用链，几乎不用改代码。
5. **排错顺序：指标定位服务 → 链路定位环节 → 日志定位原因**。
