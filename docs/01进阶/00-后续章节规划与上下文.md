## 2. 本季目标与非目标

### 2.1 目标

把单体商城最核心的三块地基打穿：

1. **认证**：谁能登录、登录凭证如何签发和校验、如何失效。
2. **授权**：登录后能做什么、角色和权限如何建模、接口级和方法级鉴权。
3. **交易**：C 端用户、购物车、下单、库存、支付、订单状态流转。

## 3. 设计决策记录（ADR）

> 这些决策已经和你确认过。后续章节不要擅自改变；要改先回来更新本节。

### ADR-01 鉴权路线：先手写，再用 Spring Security 重写

- 第 01 章：`HandlerInterceptor` + JWT + 自定义 `UserContext`（ThreadLocal）+ BCrypt。
- 第 02 章前半：自定义 `@RequirePermission` + AOP。
- 第 02 章后半：用 Spring Security 6 重写认证与授权。
- 目的：先看清原理，再学企业主流框架；两套代码形成对照。

### ADR-02 账号模型：后台账号与 C 端账号分表

- `sys_user`：商家/管理员，参与 RBAC。
- `app_user`：消费者，只有登录态和个人资料，不参与后台 RBAC。
- 两张表、两套登录接口、两种 token（用 `userType` claim 区分）。
- 不共用一张 `user` 表 + `user_type`，避免字段和权限模型互相污染。

### ADR-03 商家模型：单商家

- 后台就是这一家店的管理员，不做 `merchant_id`、不做多租户、不做数据隔离。
- `product` 表结构本季不变。
- 多商家改造放附录 C：加 `merchant` 表、`product.merchant_id`、MyBatis-Plus 租户插件。

### ADR-04 交易深度：完整闭环，拆两章

- 第 05 章：下单、价格/库存快照、原子扣库存、幂等、取消回补。
- 第 06 章：模拟支付、订单状态机、发货、确认收货、超时关单、商家订单管理。
- 不做退款/售后，放附录 C。

### ADR-05 前端：不做

- 所有验收用 curl / IntelliJ HTTP Client / SQL / 日志。
- 现有 Vue 验收台会因路径迁移失效，这是已知代价。

### ADR-06 中间件：本季不引入

- 不用 Redis、Kafka、Nacos、Docker。
- 需要“缓存/锁/延迟队列”的地方，先用 MySQL + Spring 自带能力实现，并在“坑”里说明多实例下的问题，为后续章节留钩子。

### ADR-07 权限模型：扁平权限码

- 权限就是字符串，例如 `product:read`、`order:ship`。
- 不做 `parent_id`、菜单树、按钮类型；没有前端，菜单树没有落地场景。
- 角色是权限的集合；用户通过角色获得权限。

### ADR-08 token 失效：tokenVersion

- `sys_user.token_version` / `app_user.token_version`。
- JWT 里带 `tokenVersion`；每次请求与数据库比对。
- 登出、改密、禁用账号时 `token_version + 1`，旧 token 立即失效。
- 代价：登出会让该账号所有设备下线。对后台管理账号可接受；C 端如需单设备登出，附录 C 讲 jti 黑名单。

### ADR-09 订单号：应用层生成 + 唯一索引

- 格式：`yyyyMMddHHmmss` + 6 位随机/序列，例如 `20261112183000123456`。
- 数据库 `order_no` 唯一索引兜底；冲突时重试。
- 分布式 ID（雪花、号段）留到第 07 章，不在本季展开。

### ADR-10 超时关单：`@Scheduled` 扫表

- 每分钟扫描 `status=0 AND create_time < now - timeout` 的订单。
- 条件更新 `status=0 -> 5`，更新成功才回补库存，保证幂等。
- 多实例重复执行的问题在“坑”里说明；Redis 分布式锁 / MQ 延迟消息留到后续章节。

### 4.3 通用字段约定

所有**业务主表**（`sys_user`、`sys_role`、`sys_permission`、`app_user`、`user_address`、`orders`、`product`）统一带：

```sql
version      INT      NOT NULL DEFAULT 0 COMMENT '乐观锁版本',
deleted      TINYINT  NOT NULL DEFAULT 0 COMMENT '逻辑删除：0否 1是',
create_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
update_time  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
```

例外：

- 关联表 `sys_user_role`、`sys_role_permission`：硬删除，只留 `create_time`，不要 `version/deleted`。
- 流水表 `sys_login_log`、`sys_operation_log`、`order_status_log`、`payment_record`：只追加，不更新，不要 `version/deleted`。
- 购物车 `cart_item`：硬删除，避免“逻辑删除 + 唯一索引”导致无法重复加购。
- 金额统一 `DECIMAL(10,2)`（订单主表可用 `DECIMAL(12,2)`），禁止 `double`。
- 状态统一 `TINYINT`，代码里用枚举，不写魔法数字。
- 时间统一 `DATETIME`，Java 用 `LocalDateTime`，JDBC URL 保持 `serverTimezone=Asia/Shanghai`。

### 5.3 统一响应

成功：

```json
{ "code": 0, "message": "成功", "data": {}, "timestamp": "2026-11-12T18:30:00" }
```

失败：HTTP 状态码表达协议层结果，`code` 表达业务层结果。

| 场景 | HTTP | code |
|---|---|---|
| 参数校验失败 | 400 | 40000 |
| 未登录 / token 缺失 | 401 | 40100 / 40102 |
| 登录失败 | 401 | 40101 |
| token 无效 / 过期 | 401 | 40103 / 40104 |
| 账号禁用 | 401 | 40105 |
| 已登录但无权限 | 403 | 40300 / 40301 |
| 资源不存在 | 404 | 40400 |
| 业务冲突 | 409 | 40900 |
| 系统异常 | 500 | 50000 |

> 说明：当前项目的 `GlobalExceptionHandler` 对 `NoResourceFoundException` 和 `Exception` 没有加 `@ResponseStatus`，所以这两类实际返回 HTTP 200。第 01 章只保证认证/授权异常返回 401/403；如果你希望 404/500 也返回正确的 HTTP 状态，可以在对应处理器上加 `@ResponseStatus`。
>
> 注意：现有 `BusinessException` 的处理器是 HTTP 400；认证异常用新的 `UnauthorizedException`（401），授权异常用 `ForbiddenException`（403）。不要把所有异常都塞进 `BusinessException`，否则 401/403 会被压成 400。

## 8. 章节规划（03～06 及附录）

> 01、02 章已经产出，本节只规划后续。每章都按“目标 → 前置 → 新增表 → 接口 → 关键代码 → 验收 → 坑”展开。

### 第 03 章：后台账号管理与操作审计

**目标**：管理员能通过接口管理后台账号、角色、权限，并能查到“谁在什么时候改了什么”。

**前置**：第 02 章完成，Spring Security + `@PreAuthorize` 已生效。

**新增表**：`sys_operation_log`。

**新增/修改接口**：

- 用户：`GET /api/admin/users`、`POST /api/admin/users`、`GET /{id}`、`PUT /{id}`、`PATCH /{id}/status`、`PUT /{id}/password/reset`、`PUT /{id}/roles`。
- 角色：`POST /api/admin/roles`、`PUT /{id}`、`DELETE /{id}`、`PUT /{id}/permissions`。
- 权限：`GET /api/admin/permissions`。
- 日志：`GET /api/admin/logs/logins`、`GET /api/admin/logs/operations`。
- 商品上下架：`PATCH /api/admin/products/{id}/status`。

**关键代码点**：

1. 用户管理：
   - 新增用户：用户名唯一、密码 BCrypt、默认 `token_version=0`、`status=1`。
   - 分配角色：先删后插，放在同一事务；校验角色存在且启用。
   - 禁用用户：`status=0` + `token_version+1`，旧 token 立即失效。
   - 重置密码：BCrypt + `token_version+1`。
   - 不允许删除自己；不允许禁用自己（可选，但建议做）。
2. 角色管理：
   - 角色编码唯一；删除前检查是否仍被用户使用（`sys_user_role`）。
   - 分配权限：先删后插，同一事务。
   - `SUPER_ADMIN` 保护：不允许删除、不允许改编码（可选）。
3. 操作日志：
   - 自定义 `@OperationLog(module="商品", action="新增")`。
   - AOP `@Around`：记录用户、URI、方法、IP、脱敏参数、业务码、耗时。
   - 使用 `@Async` 异步写入，避免拖慢业务；线程池要配置 `TaskDecorator` 传递 traceId（或用 `SecurityContext` 快照）。
   - 参数脱敏：`password`、`token`、`phone`、`idCard` 等字段替换为 `***`；请求体超过 2000 字符截断。
   - 日志写入失败不能影响业务：`try-catch`。
4. 分页查询：
   - 用户、角色、登录日志、操作日志都用 `PageResult`。
   - 关键字、状态、时间范围过滤。
5. 事务边界：
   - “分配角色/权限”是“先删后插”，必须同一事务。
   - 操作日志不要和业务放在同一个事务；异步或 `REQUIRES_NEW`。

**验收清单**：

- [ ] 新建用户并分配 `PRODUCT_ADMIN`，该用户能登录、能查商品、不能查角色。
- [ ] 禁用用户后，该用户旧 token 立即 401。
- [ ] 重置密码后，旧 token 立即 401；新密码能登录。
- [ ] 角色仍被用户使用时，删除返回业务错误 20006。
- [ ] 操作日志能查到“谁新增了哪个商品”，密码字段已脱敏。
- [ ] 登录日志能按用户名、成功/失败筛选。
- [ ] 商品上下架接口生效，C 端只看到上架商品（第 04 章验证）。

**坑**：

- `@Async` 线程拿不到 `SecurityContext` / `MDC`，要在调用前捕获用户和 traceId。
- 操作日志 AOP 和 `@Transactional` 的顺序：日志切面不要包在事务里，避免业务回滚把日志也回滚。
- 先删后插要防止空集合：`delete` 后再 `insert`，集合为空时只删不插。
- 角色删除要先查引用，不能只靠外键（本项目不一定建外键）。
- 参数脱敏不要用 `toString()` 直接拼接整个 DTO。
- 分页查询的 `pageSize` 仍要兜底上限。

**预计用时**：5～6 小时。

### 第 04 章：C 端用户与购物车

**目标**：C 端用户能注册、登录、维护地址、浏览上架商品、使用购物车；后台 token 与 C 端 token 完全隔离。

**前置**：第 03 章完成。

**新增表**：`app_user`、`user_address`、`cart_item`。

**新增接口**：

- 认证：`POST /api/app/auth/register`、`POST /api/app/auth/login`、`POST /api/app/auth/logout`、`GET /api/app/auth/me`、`PUT /api/app/users/me`。
- 商品：`GET /api/app/products`、`GET /api/app/products/{id}`（公开，只返回上架商品）。
- 地址：`GET/POST /api/app/addresses`、`PUT/DELETE /{id}`、`PUT /{id}/default`。
- 购物车：`GET /api/app/cart`、`POST /api/app/cart/items`、`PUT /api/app/cart/items/{productId}`、`DELETE /api/app/cart/items/{productId}`、`PUT /api/app/cart/checked`。

**关键代码点**：

1. 双 token 体系：
   - `JwtTokenProvider` 增加 `userType` claim（`ADMIN` / `APP`）。
   - 第 02 章的 `JwtAuthenticationFilter` 只服务 `/api/admin/**`，校验 `userType=ADMIN`。
   - 新增 `AppJwtAuthenticationFilter` 服务 `/api/app/**`，校验 `userType=APP`。
   - `SecurityConfig` 增加第三条链：`@Order(1) /api/admin/**`、`@Order(2) /api/app/**`、`@Order(3) /** permitAll`。
   - 两条受保护链分别使用 `SysUserDetailsService` 和 `AppUserDetailsService`。
2. C 端商品：
   - `AppProductController` + `AppProductVO`，只查 `status=1 AND deleted=0`。
   - VO 不返回 `contactPhone`、`version`、`deleted`；库存可以返回，用于前端提示。
   - 不要复用后台的 `ProductVO`，避免以后后台加字段泄漏到 C 端。
3. 收货地址：
   - 每个用户最多 20 条。
   - 设置默认地址：同一事务内先把该用户所有地址 `is_default=0`，再把目标地址 `is_default=1`。
   - 删除默认地址后，是否自动选一个默认？本季不做，保持“可以没有默认地址”，下单时必须显式选地址。
   - 手机号复用 `@Phone` 校验。
4. 购物车：
   - 加购：商品必须存在且上架；数量 1～99；同一商品重复加购则累加数量。
   - 更新数量：校验 1～99，且不超过当前库存（库存可能变化，下单时还要再校验一次）。
   - 列表：先查 `cart_item`，再用 `product_id` 批量查商品，避免 N+1。
   - 选中状态：`checked` 字段；支持全选/取消全选。
   - 硬删除：移除商品直接 `DELETE`，不套逻辑删除。
5. 注册/登录：
   - 手机号唯一；密码 BCrypt；注册后可直接登录。
   - 登录失败与后台一样，统一“手机号或密码错误”，不暴露账号是否存在。
   - C 端 `token_version` 机制与后台一致。

**验收清单**：

- [ ] C 端注册、登录成功，返回 `userType=APP` 的 token。
- [ ] 后台 token 调 `/api/app/**` 返回 401；C 端 token 调 `/api/admin/**` 返回 401。
- [ ] C 端商品列表只返回上架商品，详情不含 `contactPhone`。
- [ ] 加购、改数量、删除、全选/取消全选都生效；重复加购数量累加。
- [ ] 购物车列表没有 N+1（SQL 日志里商品查询是批量 `IN`）。
- [ ] 设置默认地址后，同一用户只有一条 `is_default=1`。
- [ ] 地址超过 20 条返回业务错误。
- [ ] 下架商品不能加购，已加购的商品在列表里标出“已下架”。

**坑**：

- 两条 `SecurityFilterChain` 的顺序：`@Order` 小的先匹配；`securityMatcher` 写错会导致所有请求走错链。
- `JwtAuthenticationFilter` 如果被注册成 Servlet Filter（`@Component` 且没有禁用自动注册），会执行两次；本季的做法是不加 `@Component`，在 `SecurityConfig` 里 `new`。
- `hasAuthority` 与 `hasRole` 的前缀问题在 C 端同样存在；C 端本季不做权限码，只做登录态。
- 购物车库存校验只是“提示”，下单时必须再校验，不能信任购物车里的数量。
- 地址默认切换有并发问题：两个请求同时设默认，可能两条都变成 1；本季用事务 + 最后更新覆盖，附录 C 讲悲观锁/唯一索引方案。
- C 端注册不要复用后台的 `SysUser` 实体和 Mapper，字段和语义不同。
- 手机号是敏感信息，日志和 VO 要脱敏。

**预计用时**：6～8 小时。

### 第 05 章：下单与库存事务

**目标**：C 端能从购物车下单，订单保存价格/商品/地址快照，库存原子扣减，失败整单回滚；重复提交只生成一单；取消订单回补库存。

**前置**：第 04 章完成。

**新增表**：`orders`、`order_item`、`order_submit_token`；`ALTER TABLE product_stock_log ADD COLUMN biz_no VARCHAR(64)`。

**新增接口**：

- `POST /api/app/orders/token`：获取幂等 token。
- `POST /api/app/orders`：创建订单。
- `GET /api/app/orders`：我的订单分页。
- `GET /api/app/orders/{orderNo}`：订单详情。
- `POST /api/app/orders/{orderNo}/cancel`：取消待支付订单。

**关键代码点**：

1. 幂等 token：
   - `POST /api/app/orders/token` 生成 UUID，写入 `order_submit_token` 表（id, user_id, token, used, expire_time, create_time）。
   - 本节已把 `order_submit_token` 列入第 4 节表清单，本章生成时不要再改回 `orders.submit_token`。
   - 提交时校验 token 属于当前用户、未使用、未过期；创建订单成功后标记 `used=1`；重复提交返回已有订单或 30005。
   - 订单创建失败时事务回滚，token 仍然是 `used=0`，用户可以重试；这是期望行为。
2. 下单主流程（同一事务）：
   - 校验地址属于当前用户，保存地址快照。
   - 查询选中的购物车项；为空则 30001。
   - 逐项校验商品存在、上架、库存足够；计算单价和小计（**以数据库价格为准，不信任前端**）。
   - 插入 `orders`（状态 0 待支付）、`order_item`（快照）。
   - 逐项原子扣库存：`UPDATE product SET stock = stock - ? WHERE id=? AND stock>=? AND deleted=0 AND status=1`；影响行数为 0 则抛业务异常，整单回滚。
   - 写 `product_stock_log`，`biz_no=order_no`，`reason='下单扣减'`。
   - 删除已下单的购物车项（或标记，本季直接删）。
   - 标记幂等 token 已使用。
3. 订单号：
   - `OrderNoGenerator`：`yyyyMMddHHmmss` + 6 位随机数；`order_no` 唯一索引；插入冲突时重试 3 次。
   - 不要用 `System.currentTimeMillis()` 单独做单号，可能重复。
4. 取消订单：
   - 条件更新：`UPDATE orders SET status=4, close_time=NOW(), cancel_reason=? WHERE order_no=? AND user_id=? AND status=0`。
   - 影响行数为 1 才回补库存；为 0 说明已被支付/已取消/不属于当前用户，返回 30004。
   - 回补库存：`UPDATE product SET stock = stock + ? WHERE id=?`；写 `product_stock_log`，`biz_no=order_no`，`reason='取消回补'`。
   - 回补必须幂等：靠“状态条件更新成功”保证只执行一次。
5. 查询：
   - 我的订单分页：按 `user_id + status` 过滤，时间倒序。
   - 订单详情：校验 `order_no` 属于当前用户；后台查询不校验用户，但要校验权限。
   - 订单 VO 包含 `orderNo`、状态、金额、商品行、地址快照、时间。
6. 事务与锁：
   - 下单方法 `@Transactional(rollbackFor = Exception.class)`。
   - 不要在事务里调用支付、短信、MQ；本季没有这些，但要在注释里留位置。
   - 库存扣减用原子 SQL，不要“先查再减”。
   - 事务尽量短：先做校验和计算，再开事务写库？本季为了简单，整个下单一个事务；在“坑”里说明长事务风险。

**验收清单**：

- [ ] 正常下单：订单、明细、库存流水都生成；库存减少；购物车对应项删除。
- [ ] 价格快照：下单后改商品价格，订单明细里的价格不变。
- [ ] 库存不足：整单回滚，订单/明细/流水都不落库，库存不变。
- [ ] 重复提交同一个幂等 token：只生成一单，第二次返回已有订单或 30005。
- [ ] 并发下单同一件库存：不超卖，失败方整单回滚。
- [ ] 取消待支付订单：状态变 4，库存回补，流水有“取消回补”。
- [ ] 重复取消：第二次返回 30004，库存不会再次回补。
- [ ] 已支付订单不能取消（第 06 章验证）。
- [ ] 下架商品不能下单；地址不属于当前用户返回业务错误。

**坑**：

- 信任前端传的价格/金额：必须用数据库价格重算。
- 先查库存再更新：并发超卖；必须原子 `UPDATE ... WHERE stock >= ?`。
- `@Transactional` 自调用失效：下单方法不要在自己类里被另一个方法直接调用。
- 幂等 token 和订单在同一个事务：失败回滚后 token 也回滚，用户可以用同一个 token 重试；这是期望行为，但要讲清楚。
- `DuplicateKeyException` 捕获后要继续抛业务异常，不能吞掉。
- 取消回补库存没有状态条件：重复取消会多次加库存。
- 订单号冲突重试：唯一索引 + 捕获异常，不要用 `synchronized`。
- 长事务：校验、远程调用、日志都放到事务外；本季日志用 AOP 异步。
- `product_stock_log` 加 `biz_no` 后，历史数据为 NULL，查询要兼容。

**预计用时**：8～10 小时。

### 第 06 章：支付、状态机与订单管理

**目标**：订单状态按状态机流转；模拟支付；商家发货；用户确认收货；超时未支付自动关单并回补库存；后台能按条件查单。

**前置**：第 05 章完成。

**新增表**：`payment_record`、`order_status_log`。

**新增接口**：

- `POST /api/app/orders/{orderNo}/pay`：模拟支付。
- `POST /api/app/orders/{orderNo}/confirm`：确认收货。
- `GET /api/admin/orders`：后台订单分页。
- `GET /api/admin/orders/{orderNo}`：后台订单详情。
- `POST /api/admin/orders/{orderNo}/ship`：发货。

**关键代码点**：

1. 订单状态枚举与状态机：
   - `OrderStatus`：0 待支付、1 已支付、2 已发货、3 已完成、4 已取消、5 已关闭。
   - `OrderStateMachine.canTransit(from, to)`：
     - 0 → 1（支付）、0 → 4（用户取消）、0 → 5（超时关闭）
     - 1 → 2（商家发货）
     - 2 → 3（用户确认收货）
     - 其他一律拒绝。
   - 所有状态变更走同一个 `transit` 方法，写 `order_status_log`。
2. 状态变更的并发控制：
   - 条件更新：`UPDATE orders SET status=#{to} WHERE order_no=#{orderNo} AND status=#{from}`。
   - 影响行数为 1 才写状态流水、执行后续动作（如回补库存）。
   - 支付与超时关单并发：只有一个能把 0 改成目标状态，另一个影响 0 行，直接返回“状态已变化”。
3. 模拟支付：
   - 校验订单属于当前用户、状态 0、金额一致。
   - 插入 `payment_record`（`order_no` 唯一），状态 1。
   - 条件更新订单 0 → 1，写 `pay_time`。
   - 重复支付：如果订单已是 1，且支付记录存在，返回成功（幂等）；不要重复插入。
   - 真实支付要讲：签名、异步回调、对账、回调幂等；本季只做 mock。
4. 商家发货：
   - 校验权限 `order:ship`。
   - 条件更新 1 → 2，写 `ship_time`。
   - 非已支付状态返回 30004。
5. 用户确认收货：
   - 条件更新 2 → 3，写 `receive_time`。
   - 只有订单所属用户能确认。
6. 超时关单：
   - `@EnableScheduling` + `@Scheduled(fixedDelay = 60000)`。
   - 查询 `status=0 AND create_time < now - timeout`，每批 100 条。
   - 逐单条件更新 0 → 5，成功才回补库存、写流水、写状态日志。
   - 时间从配置读：`mall.order.timeout-minutes: 30`。
   - 多实例重复执行：本季单实例；坑里说明用 Redis 锁 / MQ 延迟消息 / 分布式调度。
7. 后台订单查询：
   - 分页 + 订单号、用户 ID、状态、时间范围过滤。
   - 详情包含明细、支付记录、状态流水。
8. 状态流水：
   - 每次变更写 `order_status_log`，记录 from/to/operatorType/operatorId/reason。
   - 排查“谁把订单改了”时非常有用。

**验收清单**：

- [ ] 待支付订单支付成功，状态 0→1，支付记录、状态流水各一条。
- [ ] 重复支付返回成功或“已支付”，不重复写支付记录。
- [ ] 已支付订单不能取消，返回 30004。
- [ ] 商家发货 1→2；未支付订单发货返回 30004。
- [ ] 用户确认收货 2→3；非本人订单返回 404/403。
- [ ] 非法流转（0→3、2→1 等）全部被拒绝。
- [ ] 超时未支付订单被定时任务关闭，状态 0→5，库存回补，流水有记录。
- [ ] 支付与超时关单并发：只有一个成功，库存只回补一次。
- [ ] 后台能按订单号、状态、用户 ID 查单。
- [ ] `order_status_log` 能串起完整状态变化。

**坑**：

- 状态更新用“先查再改”：并发下会双写；必须条件更新。
- 支付回调重复：真实支付回调会重试，必须幂等；本季 mock 也要按幂等设计。
- 定时任务和用户支付同时发生：条件更新是唯一裁判。
- 定时任务多实例重复执行：本季说明，不解决；后续用 Redis 锁/MQ。
- `@Scheduled` 方法里抛异常：默认会中断本次执行，但下一次还会跑；要逐单 try-catch，避免一条坏单卡住整批。
- 事务里调用定时任务/支付网关：不要在事务里做远程调用。
- 时间边界：`create_time < now - timeout` 用数据库时间还是应用时间？统一用应用时间，注意时区。
- 发货/确认收货要校验操作人：后台用权限，C 端用 `user_id`。
- 订单金额与支付金额不一致：拒绝，返回 30006。

**预计用时**：8～10 小时。

## 9. 统一代码约定

### 9.1 依赖注入与 Lombok

- 统一构造器注入：`@RequiredArgsConstructor` + `private final`。
- 不用 `@Autowired` 字段注入。
- Service 实现加 `@Slf4j`；日志用 `{}` 占位符。
- 实体用 `@Getter/@Setter`，不用 `@Data`（避免 `equals/hashCode` 把 `version/deleted` 算进去）。
- DTO 可以用 `@Data`，但密码字段加 `@ToString.Exclude`。

### 9.2 校验

- Controller 入参：`@Valid @RequestBody` 或 `@Valid` Query DTO。
- 路径变量/单参数：类上加 `@Validated`，参数加 `@Min` 等。
- 业务规则（如“最低价不能大于最高价”）放 Service，抛 `BusinessException`。
- 认证失败抛 `UnauthorizedException`（401）；授权失败抛 `ForbiddenException`（403）；普通业务失败抛 `BusinessException`（400）。

### 9.3 事务

- 写方法加 `@Transactional(rollbackFor = Exception.class)`。
- 读方法不加事务。
- 不要在事务里做远程调用、发消息、写日志文件。
- 注意自调用失效：同类方法直接调用不经过代理。
- 状态流转用条件更新，不依赖“先查后改”。
- 长事务拆分：校验/计算在事务外，写库在事务内；本季下单可以一个事务，但要在文档里说明风险。

### 9.4 MyBatis-Plus

- 简单单表用 `BaseMapper` + `LambdaQueryWrapper`。
- 多表关联/复杂统计用 `@Select` 或 XML，SQL 里用 `#{}`。
- 分页必须注册 `PaginationInnerInterceptor`。
- 逻辑删除字段统一 `deleted`；关联表和购物车用硬删除，要在文档里说明原因。
- 乐观锁字段统一 `version`；`updateById` 冲突时检查影响行数。
- 自动填充 `create_time/update_time` 由 `MyMetaObjectHandler` 负责；流水表手动设置时间。

### 9.5 VO 与敏感字段

- 实体永不直接返回。
- 后台 VO 和 C 端 VO 分开：`AdminProductVO` / `AppProductVO`。
- VO 不包含：`passwordHash`、`tokenVersion`、`version`、`deleted`。
- 手机号、身份证等敏感字段：返回前脱敏，日志里不打印。
- DTO 只包含允许前端传的字段：例如修改商品不允许直接改库存。

### 9.6 日志

- 业务日志只打定位字段：`userId`、`productId`、`orderNo`，不要 `log.info("dto={}", dto)`。
- 异常：业务异常 `warn` 不打堆栈；系统异常 `error` 打完整堆栈。
- 认证失败：记录用户名、IP、原因，不记录密码/token。
- 操作日志：AOP 异步写入，参数脱敏。
- traceId：`TraceIdFilter` 写入 MDC；异步线程要手动传递。

### 9.7 安全

- 密码：BCrypt，禁止 MD5/SHA/明文。
- JWT：HS256，密钥 ≥32 字节，生产从环境变量读。
- token 只放 `userId`、`username`、`userType`、`tokenVersion`；不放权限列表（避免权限变更后 token 仍生效）。
- `Authorization: Bearer <token>`；不要放 URL。
- 登录失败统一提示，不暴露账号是否存在。
- 认证异常 401，授权异常 403；不要把 401/403 压成 400/500。
- 生产关闭 SQL 日志、健康检查详情、dev 实验室接口。

### 9.8 验收

每章至少三组验证：

1. **正常路径**：200 + `code=0`，SQL/日志符合预期。
2. **异常路径**：未登录、无权限、参数错、重复提交、非法状态。
3. **边界/并发**：过期 token、库存刚好扣完、支付与关单同时发生。

每章至少设计 3 个“故意制造的错误”，并给出排错表。
