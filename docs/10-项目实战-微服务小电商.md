# 第 10 章 项目实战：微服务小电商

> 预计用时：20 小时（建议分 4-6 次完成）
> 本章把前面所有技术串起来。不要只看，必须自己敲、自己跑、自己压测。

## 10.1 项目目标

做一个**能演示、能讲清楚、能写进简历**的微服务项目，覆盖：

- 服务拆分与注册发现（Nacos）
- 统一网关与鉴权（Gateway）
- 服务调用与容错（OpenFeign + Sentinel）
- 缓存（Redis）
- 消息队列（Kafka）
- 幂等与分布式事务（本地消息表）
- 容器化部署（Docker Compose）
- 可观测性（traceId + Prometheus + Zipkin）

**不追求功能多**，追求每个技术点都有明确的落地位置和可验证的效果。

## 10.2 需求说明

### 10.2.1 角色与功能

| 角色 | 功能 |
|---|---|
| 用户 | 注册、登录、查看商品、下单、查看我的订单 |
| 管理员 | 商品上架/下架、修改库存（简化：直接调接口） |
| 系统 | 下单后异步加积分、超时未支付取消订单（选做） |

### 10.2.2 核心业务流程

```text
用户浏览商品
  → 商品详情（走 Redis 缓存）
  → 提交订单（带幂等号 requestNo）
      → 网关鉴权，解析 userId
      → 订单服务校验商品、库存
      → 创建订单（唯一索引防重复）
      → 调用商品服务扣库存（条件更新防超卖）
      → 写本地消息表
      → 返回订单号
  → 定时任务发送 Kafka 消息
      → 积分服务消费，幂等加积分
      → 短信服务消费，发送通知（模拟）
```

### 10.2.3 非功能要求

| 要求 | 目标 |
|---|---|
| 下单接口 P99 | < 500ms（不含异步） |
| 库存 | 不超卖 |
| 幂等 | 同一 requestNo 重复提交只创建一个订单 |
| 可用性 | 商品服务挂掉时，下单返回友好提示，不雪崩 |
| 可观测 | 一次下单的所有日志能用 traceId 串起来 |
| 部署 | `docker compose up -d` 一键启动 |

## 10.4 数据库设计

完整脚本见 `docker/mysql/init.sql`。核心表：

### 10.4.1 商品表

```sql
CREATE TABLE product (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  name        VARCHAR(64)     NOT NULL,
  price       DECIMAL(10, 2)  NOT NULL,
  stock       INT             NOT NULL DEFAULT 0,
  status      TINYINT         NOT NULL DEFAULT 1,
  version     INT             NOT NULL DEFAULT 0,
  deleted     TINYINT         NOT NULL DEFAULT 0,
  create_time DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  KEY idx_name (name),
  KEY idx_status_price (status, price)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

### 10.4.2 订单表

```sql
CREATE TABLE orders (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  user_id     BIGINT UNSIGNED NOT NULL,
  product_id  BIGINT UNSIGNED NOT NULL,
  quantity    INT             NOT NULL,
  amount      DECIMAL(12, 2)  NOT NULL,
  status      VARCHAR(16)     NOT NULL DEFAULT 'CREATED',
  request_no  VARCHAR(64)     NOT NULL,
  create_time DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_user_request (user_id, request_no),   -- 幂等
  KEY idx_user_status_time (user_id, status, create_time)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4;
```

### 10.4.3 本地消息表

```sql
CREATE TABLE local_message (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  biz_id          VARCHAR(64)     NOT NULL,
  topic           VARCHAR(64)     NOT NULL,
  payload         TEXT            NOT NULL,
  status          TINYINT         NOT NULL DEFAULT 0,   -- 0待发送 1已发送 2已消费 3失败
  retry_count     INT             NOT NULL DEFAULT 0,

  create_time     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  update_time     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_biz_topic (biz_id, topic),

```

## 10.6 分阶段实现

不要一次写完。按下面五个阶段推进，每个阶段都能运行、能验证。

### 阶段 1：单体版本（2-3 小时）

**目标**：先把业务跑通，不引入微服务。

- 一个 Spring Boot 项目，包含用户、商品、订单；
- MySQL 单库；
- 完成登录、商品查询、下单；
- 用第 01 章的工程化结构。

**验收**：

```bash
# 登录
curl -X POST http://localhost:8080/api/users/login \
  -H "Content-Type: application/json" \
  -d '{"username":"demo","password":"123456"}'

# 查商品
curl http://localhost:8080/api/products/1

# 下单
curl -X POST http://localhost:8080/api/orders \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <token>" \
  -d '{"productId":1,"quantity":2,"requestNo":"req-001"}'
```

> 为什么先做单体？因为微服务的调试成本高，业务逻辑没跑通就拆，会把业务 bug 和分布式 bug 混在一起。

### 阶段 2：拆分服务（4-6 小时）

- 拆成 user / product / order 三个服务；
- 接入 Nacos 注册中心；
- order 通过 Feign 调 product；
- 公共模块放 Result、异常、Feign 接口。

**验收**：

- Nacos 控制台看到 3 个服务；
- 订单服务能调到商品服务；
- 停掉商品服务，订单接口返回明确错误。

### 阶段 3：网关、缓存、限流（4-5 小时）

- 接入 Gateway，所有请求走 8080；
- 网关实现 JWT 鉴权，用户信息通过 header 下传；
- 商品详情加 Redis 缓存（Cache Aside）；
- 给商品查询和下单接口配置 Sentinel 限流；
- Feign 配 fallback。

**验收**：

- 不带 token 访问下单接口返回 401；
- 商品详情第二次请求明显更快，Redis 有 key；
- 压测超过阈值返回 429；
- 停掉商品服务，订单接口返回兜底提示。

### 阶段 4：Kafka 与分布式事务（4-5 小时）

- 下单成功后写本地消息表；
- 定时任务扫描待发送消息，发到 Kafka；
- 积分服务消费，唯一索引保证幂等；
- 配置重试和死信队列。

**验收**：

- 正常下单，积分增加；
- 同一 requestNo 重复下单，只创建一个订单、只加一次积分；
- 停掉 Kafka，消息停留在待发送；重启后自动补发；
- 手动让消费者抛异常，消息进入死信队列。

### 阶段 5：部署与可观测（3-4 小时）

- 每个服务写 Dockerfile；
- 加入 docker-compose；
- 加 traceId 过滤器和 Feign 透传；
- 接入 Prometheus + Grafana + Zipkin；
- 写启动脚本和 README。

**验收**：

```bash
docker compose up -d
docker compose ps
```

一条命令启动全部服务，前端/接口能正常访问。

## 10.7 核心代码

### 10.7.1 商品服务：条件更新扣库存

```java
@Mapper
public interface ProductMapper extends BaseMapper<Product> {

    @Update("""
            UPDATE product
            SET stock = stock - #{count}, version = version + 1
            WHERE id = #{id} AND stock >= #{count} AND deleted = 0
            """)
    int decreaseStock(@Param("id") Long id, @Param("count") int count);

    @Update("""
            UPDATE product
            SET stock = stock + #{count}, version = version + 1
            WHERE id = #{id} AND deleted = 0
            """)
    int increaseStock(@Param("id") Long id, @Param("count") int count);
}
```

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void decreaseStock(Long productId, int count) {
    if (count <= 0) {
        throw new BusinessException(ResultCode.BAD_REQUEST, "扣减数量必须大于 0");
    }
    int affected = productMapper.decreaseStock(productId, count);
    if (affected == 0) {
        throw new BusinessException(ResultCode.PRODUCT_STOCK_NOT_ENOUGH);
    }
    // 删除缓存，下次读取重建
    redisTemplate.delete("product:detail:" + productId);
}
```

> **不要**先 `select` 再 `set stock = old - count`。并发下两个线程读到相同库存，会超卖。`stock >= count` 的条件更新是最终防线。

### 10.7.2 商品服务：缓存读取

```java
@Override
public ProductVO getById(Long id) {
    String key = "product:detail:" + id;

    String cached = redisTemplate.opsForValue().get(key);
    if (cached != null) {
        if ("NULL".equals(cached)) {
            throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND);
        }
        return readJson(cached);
    }

    Product product = productMapper.selectById(id);
    if (product == null || product.getStatus() == 0) {
        redisTemplate.opsForValue().set(key, "NULL", Duration.ofMinutes(2));
        throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND);
    }

    ProductVO vo = toVO(product);
    // TTL 加随机值，防止雪崩
    long ttlSeconds = 1800 + ThreadLocalRandom.current().nextInt(300);
    redisTemplate.opsForValue().set(key, writeJson(vo), Duration.ofSeconds(ttlSeconds));
    return vo;
}
```

### 10.7.3 订单服务：创建订单 + 写本地消息

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class OrderServiceImpl implements OrderService {

    private final OrderMapper orderMapper;
    private final LocalMessageMapper localMessageMapper;
    private final ProductClient productClient;
    private final ObjectMapper objectMapper;

    @Override
    @Transactional(rollbackFor = Exception.class)
    public Long createOrder(Long userId, OrderCreateDTO dto) {
        // 1. 查商品（走商品服务缓存）
        Result<ProductVO> productResult = productClient.getById(dto.getProductId());
        if (productResult.getCode() != 0 || productResult.getData() == null) {
            throw new BusinessException(ResultCode.PRODUCT_NOT_FOUND);
        }
        ProductVO product = productResult.getData();

        // 2. 校验库存
        if (product.getStock() < dto.getQuantity()) {
            throw new BusinessException(ResultCode.PRODUCT_STOCK_NOT_ENOUGH);
        }

        // 3. 创建订单（唯一索引兜底幂等）
        Order order = new Order();
        order.setUserId(userId);
        order.setProductId(dto.getProductId());
        order.setQuantity(dto.getQuantity());
        order.setAmount(product.getPrice().multiply(BigDecimal.valueOf(dto.getQuantity())));
        order.setStatus("CREATED");
        order.setRequestNo(dto.getRequestNo());
        try {
            orderMapper.insert(order);
        } catch (DuplicateKeyException e) {
            // 重复提交：返回已有订单
            Order existing = orderMapper.selectByUserAndRequestNo(userId, dto.getRequestNo());
            log.info("重复下单请求，返回已有订单 orderId={}", existing.getId());
            return existing.getId();
        }

        // 4. 扣库存
        Result<Void> decreaseResult = productClient.decreaseStock(dto.getProductId(), dto.getQuantity());
        if (decreaseResult.getCode() != 0) {
            throw new BusinessException(ResultCode.PRODUCT_STOCK_NOT_ENOUGH);
        }

        // 5. 写本地消息（与订单同一事务）
        OrderCreatedEvent event = new OrderCreatedEvent(
                order.getId(), userId, dto.getProductId(), dto.getQuantity(),
                order.getAmount(), LocalDateTime.now());
        LocalMessage message = new LocalMessage();
        message.setBizId(String.valueOf(order.getId()));
        message.setTopic("order-created");
        message.setPayload(writeJson(event));
        message.setStatus(0);
        localMessageMapper.insert(message);

        log.info("订单创建成功 orderId={}, userId={}", order.getId(), userId);
        return order.getId();
    }
}
```

> 这里仍有"事务内调 Feign"的问题（长事务）。更严格的做法是：订单先创建为 `CREATED`，扣库存异步进行，失败则取消订单。学习阶段先接受这个简化，但要能说出它的风险。

### 10.7.4 本地消息定时发送

```java
@Component
@RequiredArgsConstructor
@Slf4j
public class LocalMessageScheduler {

    private final LocalMessageMapper localMessageMapper;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 5000)
    public void sendPendingMessages() {
        List<LocalMessage> messages = localMessageMapper.selectPending(100);
        for (LocalMessage message : messages) {
            try {
                kafkaTemplate.send(message.getTopic(), message.getBizId(), message.getPayload())
                        .get(3, TimeUnit.SECONDS);
                localMessageMapper.markSent(message.getId());
                log.info("本地消息发送成功 bizId={}", message.getBizId());
            } catch (Exception e) {
                log.error("本地消息发送失败 bizId={}", message.getBizId(), e);
                localMessageMapper.markRetry(message.getId(), nextRetryTime(message.getRetryCount()));
            }
        }
    }

    private LocalDateTime nextRetryTime(int retryCount) {
        long seconds = Math.min(300, (long) Math.pow(2, retryCount));
        return LocalDateTime.now().plusSeconds(seconds);
    }
}
```

```sql
-- LocalMessageMapper
SELECT * FROM local_message
WHERE status = 0 AND (next_retry_time IS NULL OR next_retry_time <= NOW())
ORDER BY id LIMIT #{limit};
```

> 启动类加 `@EnableScheduling`。多实例部署时，定时任务要加分布式锁，避免重复发送；或者用 ShedLock/XXL-Job。

### 10.7.5 积分服务：幂等消费

```java
@Service
@RequiredArgsConstructor
@Slf4j
public class PointsConsumer {

    private final PointsRecordMapper pointsRecordMapper;

    @KafkaListener(topics = "order-created", groupId = "points-group")
    public void onOrderCreated(ConsumerRecord<String, String> record, Acknowledgment ack) {
        try {
            OrderCreatedEvent event = objectMapper.readValue(record.value(), OrderCreatedEvent.class);
            // 唯一索引 uk_order_id 保证幂等
            pointsRecordMapper.insert(new PointsRecord(
                    event.getUserId(), event.getOrderId(), event.getAmount().intValue()));
            ack.acknowledge();
            log.info("积分增加成功 orderId={}, points={}", event.getOrderId(), event.getAmount().intValue());
        } catch (DuplicateKeyException e) {
            // 重复消息，直接确认
            ack.acknowledge();
            log.info("积分已处理，忽略重复消息 offset={}", record.offset());
        } catch (Exception e) {
            log.error("积分处理失败 offset={}", record.offset(), e);
            throw e;   // 交给 ErrorHandler 重试/死信
        }
    }
}
```

> **序列化说明**：本节为了让"本地消息表存 JSON 字符串"的链路更直观，生产端用 `StringSerializer`、消费端用 `StringDeserializer`，再手动 `ObjectMapper` 转对象。如果你按第 06 章配置了 `JsonSerializer` / `JsonDeserializer`，消费者直接写 `@KafkaListener public void onOrderCreated(OrderCreatedEvent event, Acknowledgment ack)` 即可，不要混用两种配置。

## 10.11 常见问题

1. **一上来就拆 5 个服务，业务跑不通**：先单体，后拆分。
2. **服务间共享数据库表**：违背数据库私有原则，后期改表全崩。至少通过接口访问。
3. **事务里调 Feign**：长事务、锁等待、远程失败无法回滚。用本地消息表或状态机。
4. **幂等只靠前端防重复点击**：接口必须自己幂等。
5. **扣库存先查后改**：并发超卖，必须条件更新。
6. **Kafka 消费者没做幂等**：重复消息导致积分翻倍。
7. **服务挂了没有降级**：调用方线程池被拖死，雪崩。
8. **没有 traceId**：出问题只能逐个服务 grep。
9. **Docker Compose 里用 localhost 连中间件**：容器内 localhost 是容器自己，用服务名。
10. **项目只跑通没压测**：简历写了"高并发"，面试官一问就露馅。

## 10.12 本章小结

1. **项目要按阶段推进**：单体跑通 → 拆服务 → 加网关/缓存/限流 → 加 MQ/事务 → 容器化/可观测。
2. **每个技术点都要有明确的业务落点**，不是为了用而用。
3. **幂等、防超卖、降级、可观测**是微服务项目的四条生命线。
4. **测试要覆盖功能、并发、故障三类场景**，并留下数据和截图。
5. **简历和面试讲"问题-方案-结果"**，不讲技术名词堆砌。
